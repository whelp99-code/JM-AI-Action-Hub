# Action Hub 개선 계획 v2 — 실사용 결함 정리와 고도화

작성: 2026-08-05, Master(Fable). 근거: 실기기 실사용에서 발견·수정된 결함 4건 + iOS·서버 전수 코드 조사(각각 독립 수행) + 운영 인스턴스 읽기 조회.
상태: **마스터 승인 대기.** 승인 전 어떤 카드도 구현을 시작하지 않는다.

## 0. 판정

이 계획은 "발견된 모든 것을 고친다"가 아니다. 조사에서 나온 항목은 iOS 26건 + 서버 19건 + 계약 3건이지만, **실제로 사용을 막거나 사용자를 속이는 것은 그중 8건**이고 나머지는 거슬리는 수준이거나 현재 무증상이다. 이 구분을 §2~§5의 등급으로 고정한다.

### 0.1 이번 조사가 드러낸 가장 중요한 사실

**운영 인스턴스에서 백그라운드 워커가 한 번도 돌지 않았다(S1).** `jm-ai-action-hub-worker.service` 유닛 파일은 배포되어 있으나 설치되지 않았고, systemd에는 API 서버 하나만 등록되어 있다. 그 결과 재시도·follow-up 도래·APNs 발송·외부 상태 동기화가 전부 죽어 있으며, 요청이 들어와 inline drain이 걸릴 때만 우연히 처리된다.

실제 피해가 운영 데이터에 남아 있다: 실행 실패한 항목 2건이 `state=queued`, `attempts=2/5`와 `1/5`로 멈춰 있고, 마지막 감사 이벤트 이후 아무 처리도 없다. 사용자는 앱에서 "실행"을 눌렀고 성공 요약을 받았지만 외부 서비스에는 아무것도 생기지 않았다.

**단일 항목으로는 이것이 가장 투입 대비 효과가 크다.** 워커를 올리는 것만으로 멈춘 2건이 즉시 진행되고 알림·동기화 기능이 살아난다.

### 0.2 실사용 결함 4건의 공통 성질 (이미 수정됨, 재발 방지가 과제)

| 수정된 결함 | 실제 성질 |
|---|---|
| Face ID 무한 반복 | 시스템이 앱을 비활성→활성으로 만드는 것을 사용자 복귀로 오인 |
| 새로고침 `cancelled` | 플랫폼의 정상 취소를 오류로 표시 |
| 세션 복원 실패 | 저장한 데이터를 자기가 못 읽음(인코딩 왕복 비대칭) |
| 승인 후 목록 잔류 | 상태는 바꿨으나 목록 필터가 보는 파생 플래그를 안 바꿈 |

앞의 셋은 **플랫폼 신호 오독**, 넷째는 **상태와 파생 뷰의 어긋남**이다. 조사 결과 두 부류 모두 아직 남아 있다(P0-4, P1-2, P1-3, P1-4).

### 0.3 구조적 원인

iOS 앱 코드에 **자동 테스트가 0건**이다. 47개 테스트는 전부 `ActionHubCore`(네트워크·인코딩·오프라인 큐) 대상이고, `AppModel`(552줄)과 모든 화면, 인프라 클래스는 커버되지 않는다. **실기기에서 발견된 결함 4건 중 3건이 정확히 이 무테스트 영역에 있었다.** 남은 결함도 같은 곳에 있을 확률이 높다.

## 1. 이번 계획에서 정정하는 사항

**2026-08-05 "취소 오류 수정" 보고는 부정확했다.** `handle(_:)`에 넣은 `CancellationError`/`URLError.cancelled` 필터는 구조적으로 도달하지 않는다 — `HTTPTransport.swift:47`이 모든 예외를 `ActionHubAPIError.transport(...)`로 래핑하기 때문이다. 증상이 사라진 것은 함께 넣은 `refreshAllDetached()`(제스처 취소 비상속) 덕분이지 필터 덕분이 아니다. 취소 가능 컨텍스트가 남은 4곳에서 증상이 재현될 수 있다. P1-2에서 근본 수정한다.

## 2. P0 — 지금 사용을 막거나 사용자를 속이는 것

### P0-1. 백그라운드 워커 설치 [서버 운영]
**증상:** 재시도·follow-up·푸시·외부 동기화가 동작하지 않는다. 실행 실패 항목 2건이 운영 DB에 멈춰 있다.
**근거:** `server/deploy/systemd/jm-ai-action-hub-worker.service` 존재, 원격 systemd 미등록. `worker.py:68 run_forever()`가 유일한 주기 실행 경로.
**작업:** 유닛 설치·기동·재부팅 지속성 확인. 기동 후 멈춘 2건이 실제로 진행되는지 관찰.
**검증:** `systemctl --user is-active`, 멈춘 항목의 `attempts` 증가 또는 종결, follow-up 도래 처리 확인.

### P0-2. 실행 실패를 응답에 드러내기 [서버]
**증상:** 커넥터가 실패해도 `200 {queued: 1, failed: 0}`. 사용자는 성공으로 오인한다.
**근거:** `services/outbox.py:198`이 재시도 시 state를 `QUEUED`로 유지하고 `execution_error`만 채운다. `api/mobile.py:100-127`의 집계는 `FAILED`만 실패로 센다.
**작업:** `ExecutionSummary`에 재시도 중·오류 보유 항목을 노출한다(오늘 `blocked_item_ids`를 추가한 방식과 동일한 원칙 — 200 응답이 문제를 숨기지 않게). iOS가 그것을 표시한다.
**검증:** 커넥터 실패를 유도한 뒤 응답과 화면에 실패가 드러나는지.

### P0-3. 검토 게이트 우회 제거 [iOS]
**증상:** 서버의 구조적 검토 게이트가 모바일에서 무력화되어 있다. 운영 데이터에 우회 사례가 남아 있다(캘린더 항목인데 시작 시각이 없어 검토 대상인데도 승인·실행되어 실패).
**근거:** `AppModel.swift:307-311`이 `forceReviewItems: true`를 하드코딩. `executor.py:119`의 차단 분기가 iOS 경로에서 성립할 수 없고, `AppModel.swift:318`의 `blockedItemIds` 처리는 도달 불가능한 죽은 코드다.
**작업:** 기본을 `false`로 바꾸고, 차단이 발생하면 사용자에게 이유를 보여준 뒤 **명시적으로 강제할 때만** `true`로 재요청한다.
**검증:** 검토 필요 항목 승인 시 차단 안내가 뜨고, 강제 선택 시에만 통과.

### P0-4. 앱 영구 잠금 탈출 경로 [iOS]
**증상:** 생체인증 평가가 불가능한 상태(기기 암호 미설정, 생체 lockout, 하드웨어 오류)에서 앱이 잠금 화면에서 나올 수 없다. 버튼을 눌러도 무반응·무메시지. 잠금 해제 설정은 접근 불가능한 설정 화면 안에 있다. 복구는 재설치뿐이고 그러면 페어링이 소실된다.
**근거:** `BiometricLock.swift:43-47`이 `canEvaluatePolicy` 실패 시 오류를 버리고 잠금 유지. `RootView.swift:24-28`이 잠금 상태에서 `LockView`만 렌더링.
**작업:** 평가 불가 사유를 사용자에게 보여주고, 기기 암호 인증 대체 경로 또는 잠금 기능 자체를 끄는 탈출구를 제공한다. 최소한 "왜 안 되는지"와 "무엇을 하면 되는지"를 표시한다.
**검증:** 생체 lockout을 유발한 뒤 앱에 진입할 수 있는지(실기기 필요).

## 3. P1 — 조용한 오작동 (시스템을 믿을 수 없게 만듦)

### P1-1. 알림 설정이 서버 값을 못 읽음 [iOS]
`JSONCoding.swift:16`의 `convertFromSnakeCase`가 딕셔너리 **내부 키까지** 변환하는데 `APIModels.swift:714-720`은 snake_case 키로 조회한다. 결과적으로 서버 값이 항상 무시되고 전부 켜진 것으로 표시된다. 저장하면 서버 값이 되돌아간다. 테스트 픽스처가 전부 빈 객체라 회귀 테스트에 잡히지 않았다.
**작업:** 전용 Codable 구조체로 교체(딕셔너리 키 변환에 의존하지 않게). 실제 값이 든 픽스처로 테스트 추가.

### P1-2. 취소 처리 근본 수정 [iOS]
`HTTPTransport.swift:47`이 취소를 일반 전송 오류로 래핑한다. 취소를 별도 오류 종류로 보존하고, 상위에서 그것만 무시하도록 고친다. 잔여 취소 경로 4곳(`PlanDetailView.swift:75`, `DayCloseView.swift:65`, `SettingsView.swift:102`, `BackgroundSyncManager.swift:32`)이 함께 해소된다.

### P1-3. 재진입 가드 [iOS]
`scenePhase == .active`마다 `refreshAll()`이 무가드로 실행된다. 시스템 시트(권한·공유·카메라)가 닫힐 때마다 7개 요청이 추가 발사되고, 콜드 런치 시에는 두 경로가 동시에 돌아 14개가 된다. 늦게 끝난 응답이 먼저 끝난 응답을 덮어써 값이 되돌아가 보일 수 있다.
**작업:** `refreshAll()`에 진행 중 가드를 넣고, 시작 경로와 포그라운드 경로의 중복을 없앤다.

### P1-4. `needs_review` 해제 일원화 + 목록 필터 정정 [서버]
오늘 승인·거부는 고쳤으나 같은 부류가 4곳 더 있다: 포커스 세션 완료(`focus.py:831`), day-close 취소(`focus.py:937`), follow-up 해결(`followups.py:186`), 외부 동기화 완료·취소(`state_sync.py:204`). 모두 `item.state`는 바꾸면서 `needs_review`를 남긴다.
또한 목록 필터(`mobile.py:77-96`, `:163-170`)가 **terminal state를 배제하지 않는다** — 이것이 근본 원인이다.
**작업:** 상태 전이 헬퍼 한 곳에서 `needs_review`를 해제하고, 목록 필터에서 terminal state를 배제한다. 후자만으로도 미래의 같은 결함이 전부 막힌다.

### P1-5. 액션 후 화면 갱신 [iOS]
- `updateItem`만 갱신 트리거가 없다(`AppModel.swift:297-302`). 다른 액션은 모두 `refreshAll`/`refreshFocus`를 부른다. "계속 검토 필요"를 끄고 저장해도 배지·목록이 그대로다.
- 승인·제외 후 상세 화면에 남아 버튼이 계속 활성이다(`PlanDetailView.swift:84-113`). 재승인 시 아무 메시지 없이 성공처럼 보인다.

## 4. P2 — 거슬리지만 우회 가능

한 묶음으로 처리한다. 각각은 작고 독립적이다.

| 항목 | 내용 |
|---|---|
| 빈 상태 새로고침 불가 | 검토·활동 탭은 목록이 비면 당겨서 새로고침이 불가능하다. Today 화면만 올바르게 되어 있다 |
| Focus 전 화면 새로고침 없음 | 툴바 버튼만 있고 당겨서 새로고침이 없다 |
| 원시 UUID 노출 | 커밋된 Big3 항목이 매트릭스 응답에 없으면 제목 대신 UUID가 표시된다 |
| 알림 토글 거짓 상태 | 저장하지 않고 나가도 토글이 켜진 채 남아 세션 내내 거짓 상태를 보여준다 |
| 푸시 권한 실패 침묵 | 이미 거부한 상태면 버튼을 눌러도 아무 일이 없다. 설정 앱으로 보내는 경로도 없다 |
| dead letter 복원 후 미전송 | "모두 복원" 후 전송이 시작되지 않는다 |
| 페어링 오류 미표시 | 구체적 실패 사유를 던지는데 UI가 전부 버리고 "유효하지 않다"만 표시한다 |
| 음성 인식 덮어쓰기 | 녹음 중 사용자가 텍스트를 고치면 다음 부분 결과가 덮어쓴다 |
| 배지와 목록의 단위 불일치 | 배지는 항목 수, 목록은 계획 수 |
| 검토 목록 조용한 절단 | 조인 후 `LIMIT`이 걸려 실제 반환 계획 수가 요청보다 훨씬 적을 수 있다 |
| enum repr 노출 | 활동 화면 부제에 `Destination.GITHUB` 형태가 그대로 표시된다 |
| Live Activity 오갱신 | 고아 활동을 id 대조 없이 갱신해 이전 세션 제목에 새 타이머가 붙을 수 있다 |
| 동시성 충돌이 500 | `StaleDataError` 처리가 없어 정체불명의 500이 나간다. 409로 바꾸면 재시도 안내가 가능하다 |

## 5. P3 — 고도화 (기능 추가)

**이미 서버가 지원하는데 화면만 없는 것부터** 한다. 새로 만드는 것보다 값이 크다.

| 기능 | 상태 |
|---|---|
| **항목 단위 승인·제외** | 서버가 `item_ids`를 지원하는데 iOS가 항상 `nil`로 호출한다(`PlanDetailView.swift:87,109`). 화면만 붙이면 된다 |
| **일정 필드 편집** | `dueAt`·`startAt`·`priority`·`labels`가 패치 모델에 있으나 편집 UI가 없다. 캘린더 항목의 시각을 앱에서 고칠 수 없어 P0-3의 차단과 직결된다 |
| **개별 dead letter 처리** | 단건 복원·삭제 API가 이미 있는데 UI는 "모두"뿐이다 |
| **보류/연기** | 검토 경로에 없다. 오늘 사용자가 기대했던 동작 |
| **검색·필터** | 검토·Focus 전 화면에 없다 |
| 일괄 처리 | 다중 선택 UI 없음 |
| 매트릭스에서 재분류·집중 시작 | 현재 읽기 전용 |

## 6. 구조 개선 (병행)

- **iOS 앱 로직 테스트 도입** — 최소한 `AppModel`의 상태 전이·오류 처리·갱신 트리거. 오늘 결함 4건 중 3건이 이 영역이었고, 테스트가 있었으면 전부 잡혔다.
- **`ExecutionSummary` 중복 구현 제거** — `api/mobile.py`와 `api/routes.py`에 완전 중복. 한쪽만 고치면 드리프트한다.
- **알림 종류 정합** — 서버 7종·iOS 5종·실제 발행 3종으로 어긋나 있다. 발행되지 않는 종류는 UI에서 감춘다.

## 7. 실행 순서와 묶음

**재설치가 필요한 iOS 수정은 반드시 묶어서 한 번에 배포한다.** 앱 재설치는 사용자가 앱을 못 쓰는 시간을 만들고, 페어링 유지 여부도 매번 확인해야 한다.

```
묶음 A (서버 전용, 무중단)   : P0-1 → P0-2 → P1-4 → P2 서버분
묶음 B (iOS, 1회 재설치)     : P0-3 + P0-4 + P1-1 + P1-2 + P1-3 + P1-5 + P2 앱분
묶음 C (실기기 확인, 사용자 협조): P0-4 검증, Live Activity, App Group 프로비저닝, 위젯 읽기
묶음 D (고도화)              : P3 — 서버 지원 기능부터
```

묶음 A를 먼저 하는 이유: 서버 수정은 앱을 건드리지 않고 즉시 효과가 나며, P0-1 하나로 실사용 피해가 바로 멈춘다.

## 8. 이번에 하지 않을 것 (명시적 제외)

- **미사용 알림 종류 구현**(`deadline_risk`, `connector_failure`, `focus_ready`, `focus_overrun`) — 발행처가 없다. 구현이 아니라 UI에서 감추는 것이 맞다.
- **다른 클라이언트 대비 수정**(마이크로스텝 요청 무시, day-close 부분 무처리) — 현재 iOS 사용 패턴에서 무증상이다.
- **낙관적 동시성 전면 재설계** — 단일 사용자 환경이라 위험이 낮다. 500을 409로 바꾸는 것만 P2에 넣는다.
- **certificate pinning, 첨부 공유, delta sync 등** — `docs/12_KNOWN_LIMITATIONS_KR.md`에 의도적 제외로 이미 명시되어 있다.
- 사소 항목 8건(F-19~F-26) — 사용자가 실제로 겪었다고 보고하기 전에는 손대지 않는다.

## 9. 미해결 질문 (마스터 확인 필요)

1. **P0-3의 기본 동작** — 검토 필요 항목을 승인하려 할 때, 차단하고 이유를 보여준 뒤 강제 여부를 묻는 것이 맞는가? 아니면 지금처럼 통과시키되 경고만 남기는가? (전자를 권고한다 — 안전장치가 존재하는 이유가 있다)
2. **P3 우선순위** — 일정 필드 편집이 P0-3과 직결된다(시각이 없어 차단되는데 앱에서 고칠 수 없다). P3에서 끌어올릴지 판단 필요.
3. **iOS 테스트 도입 범위** — `AppModel`만인지, 화면 스냅샷까지인지. 후자는 유지 비용이 크다.
